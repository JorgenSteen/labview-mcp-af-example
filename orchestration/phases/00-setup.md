# Phase 00: session start, git, the product folder, skill setup, empty project

**Type:** setup (part by the manager, part by one agent)
**Reads:** `requirements/README.md`, `01-requirements.md` §1 and §3, `02-specification.md` §1, §2,
§9; `04-decisions.md`; the skill's `SKILL.md`, `session/start.md`, `conventions/setup.md`,
`conventions/dot-labview.md`.
**Scope:** the repo root (git only), `zuehlke-mcp-af-test-results/` (created here), `runs/<run>/`.

## Goal

Everything later phases assume: LabVIEW and labview-mcp answer, the repo is under git, the
product folder `zuehlke-mcp-af-test-results/` exists and looks like a normal LabVIEW repo, the
skill's `.labview/` inside it has the conventions settled, an empty project with the six virtual
folders opens, and the run folder exists.

**The product folder does not exist before this phase.** Everything in it is created from
`requirements/` and from the skill. That is what makes a reset a plain delete.

## Steps

1. **Manager:** create `runs/run-NN-<date>/` with `status.md` from `orchestration/status-template.md`,
   empty `briefs/`, `reports/`, `mcp-reports/`, `cost.md`, `findings.md`.
2. **Manager:** `git init` at the repo root if it is not a repository; commit everything present.
3. **Manager:** create the product folder skeleton (no LabVIEW needed):
   - `zuehlke-mcp-af-test-results/README.md`: what the application is (three paragraphs from
     `01` §1), the LabVIEW version, how to open `src/Zuehlke MCP.lvproj`, how to run the launchers,
     and one line saying the code was generated by the test described one folder up.
   - `zuehlke-mcp-af-test-results/.gitignore`: the LabVIEW and OS sections of the root
     `.gitignore`, plus `output/*`, `!output/.gitkeep` and `proof/`.
   - `zuehlke-mcp-af-test-results/.gitattributes`: a copy of the root `.gitattributes`. Both
     files are there so the product folder stays a complete repository on its own.
   - `src/`, `src/errors/`, `output/.gitkeep`, `docs/`, `tools/`, `proof/`.
   - `src/errors/ZM-errors.txt`: byte-exact copy of `requirements/assets/ZM-errors.txt`.
   - `docs/error-codes.md`: copy of `requirements/assets/error-codes.md` (its VI names are the
     original's snake_case; the agent that first raises 5000 renames them to the `02` names).
   - `tools/jsonl_viewer.html`: copy of `requirements/assets/jsonl_viewer.html`.
   - Commit: `chore: product folder skeleton`.
4. **Manager:** `session/start.md`: LabVIEW and the labview-mcp service answer; read `lvai_status`;
   write the machine facts into `status.md`. Note the LabVIEW version and the save version it
   reports; they go into `project.json`.
5. **Manager, up front:** ask the user for the one go-ahead this phase may need: copying
   `ZM-errors.txt` into LabVIEW's `user.lib\errors\` (outside the repo) and the restart that makes
   LabVIEW read it. Quote the answer in the brief. Without it, *Explain Error* will not know
   code 5000; the tests do not depend on that.
6. **Agent:** run the skill's `conventions/setup.md` **with `zuehlke-mcp-af-test-results/` as
   the skill's `<repo>`** (its `.labview/` goes there; git commands run from inside it and reach
   the outer repository), with these answers, so it asks nothing:
   - first-contact question (analysis depth): **none**, there is no code yet; but
     `conventions_mode` is **full**, the conventions come from the defaults and the decided rules.
   - every concern: **accept the defaults**; `configuration`: **no configuration files** (D34),
     mark the concern as answered.
   - record the **decided** rows of `04-decisions.md` (D3, D4, D14, D15, D16, D18, D34, D35, D36,
     D37) in `.labview/decisions.md` and as `decided` rules in the concern files they name.
   - `project.json` (paths relative to the product folder, forward slashes): `project_name`
     "Zuehlke MCP", `prefix` "ZM", `source_root` "src", `project_file` "src/Zuehlke MCP.lvproj",
     `labview_version` and `save_version` from `lvai_status`, `git` true, `conventions_mode`
     "full", `analysis_depth` "none", `proof_folder` "proof", `proof_prefix` "ZMP-",
     `briefs_folder` "../runs/<run>/briefs", `status_file` "../runs/<run>/status.md",
     `mcp_reports_folder` "../runs/<run>/mcp-reports", `knowledge_files` [],
     `restart_go_ahead` "ask".
   - `checks.json`: the seven test VIs of `03-acceptance.md` §1 by their future paths under
     `src/tests/`, and the runs of §2 that a VI can drive (R-normal ×3, R-error).
7. **Agent:** create `src/Zuehlke MCP.lvproj` through LabVIEW (never by hand) with the virtual
   folders `common`, `hardware`, `protocol`, `actors`, `tests`, `receiver`; with the go-ahead, copy
   `ZM-errors.txt` into `user.lib\errors\`.
8. **Agent:** close the project (`lvai_close_active_project` with the project path), report.

## Done when

- `lvai_status` answered; machine facts in `status.md`.
- The product folder exists with README, .gitignore, the three copied assets and the empty
  folders; nothing else in it yet beyond what the next bullets name.
- `zuehlke-mcp-af-test-results/.labview/project.json`, `decisions.md`, `checks.json` and the
  seven `conventions/*.md` exist; `decisions.md` holds the ten decided rules; `configuration.md`
  says no configuration files; the three run-folder paths point up into `runs/<run>/`.
- `zuehlke-mcp-af-test-results/src/Zuehlke MCP.lvproj` exists, opens without a missing-item
  dialog, holds the six virtual folders, is saved in the project's save version.
- Everything committed: `chore: .labview conventions and empty project`.

## Notes

- Opening a project writes it (`.lvproj` and `.lvlps`); that is why `.lvlps` is git-ignored.
- The skill's setup normally asks the user per concern; the brief carries the answers above and
  tells the agent to ask nothing it has an answer for.
- `<project folder>` in the requirements means the product folder, so the error log is
  `zuehlke-mcp-af-test-results/output/ZM-error_log.txt`.
- Nothing in `src/` beyond the project and the error file. No class, no VI, no library yet.
