1. What it is

Zuehlke MCP is a small LabVIEW Actor Framework application (prefix ZM). A simulated hardware object produces a measurement package every 500 ms. A tree of three actors moves each package to the output: the hardware manager reads the hardware, the root routes the package by its destination, and the communication manager publishes it. Every package ends up as one JSON line in a file per package type (output/TestPackage.jsonl) and as one UDP datagram, which a separate receiver VI can show live. There are no configuration files.

2. How it fits together

ROOT (ZM-ROOT-root) is started by a launcher. It launches the communication manager first and then the hardware manager, so the CM is ready before the first package arrives. It routes every package by its destination: Communication is forwarded to the CM, an error package for Root is shown in the errors list on its panel, and Unknown and Hardware are dropped with one line in the error log. Its panel holds the Stop button for the whole application.

HWM (ZM-HWM-hardware_manager) owns the hardware object: the simulated hardware ZM-HW-SIM-simulated_hardware, or the bare placeholder ZM-HW-hardware in the error run. Its helper loop reads the hardware every intervalMs (500 ms), plots each package on a live panel and sends it to the HWM, which counts it and forwards it to the root.

CM (ZM-CM-communication_manager) owns one communication protocol: it opens it when it launches, publishes every package it receives, and closes it when it stops. The root gives it a multi protocol (ZM-CP-MX-multi_protocol) that holds a file logger (ZM-CP-FL-file_logger, writes output/<type>.jsonl) and a UDP sender (ZM-CP-UDP-sender, sends each line to 127.0.0.1:61557). Sending with nobody listening is silent.

The receiver (ZM-receiver.vi) is a plain VI, not an actor.

3. Requirements

  • LabVIEW 2026 Q3, 32-bit, with the Actor Framework from vi.lib. No other add-ons; the tests are plain VIs (no Caraya, LUnit or VI Tester).

4. Run it

Interactive: ZM-launcher.vi

Run ZM-launcher.vi. Its output_folder control is optional: empty means the output folder next to src. The launcher starts the root and returns at once; its error out shows whether the launch failed. Two windows open:

  • The root's panel (ZM-ROOT-helperPanel.vi): the Stop button, the errors list, and a note that points to the receiver (open the virtual folder receiver and run ZM-receiver.vi).
  • The hardware manager's panel (ZM-HWM-helperAcquisition.vi): the chart live with temperature_c and duty_percent, interval set (ms) (500) and interval measured (ms), which reads about 500.

output/TestPackage.jsonl grows by about two lines per second. To stop, press Stop on the root's panel: the root stops, the Actor Framework stops the HWM and the CM, the CM closes its file and socket, and both panels close.

Watch the stream: ZM-receiver.vi

Open the receiver folder and run ZM-receiver.vi while the tree runs. It listens on port (default 61557; the sender sends to 127.0.0.1:61557, so run it on the same PC). It shows a chart of temperature_c and duty_percent, interval measured (ms), the last line, the packets count and error out. Start it and stop it (Stop) at any time; the tree does not notice.

Headless: ZM-launcher_test.vi

It sits in the project's tests virtual folder (the file is in src/, next to ZM-launcher.vi; it is not part of the test library). It deletes the old output, launches the root, waits run_time_ms, reads the root panel's errors, sends Normal Stop and counts the lines of both files. The hardware manager's panel opens during the run as well.

5. Output

output/<type>.jsonl

One file per package type, one JSON line per package (normally only TestPackage.jsonl). The timestamp is ISO 8601 UTC with milliseconds; the UDP datagram carries the same bytes. Example:

{"timestamp":"2026-10-11T19:26:39.966Z","type":"TestPackage","destination":"Communication","data":{"temperature_c":26.000772513374347028,"sample_index":106,"duty_percent":3,"sensor_ok":true,"status":"warm"}}

output/ZM-error_log.txt

One line per entry, tab-separated: <ISO UTC timestamp>, <sender>, <code>, <source>. For example:

2026-10-11T19:27:07.682Z	ROOT	0	dropped TestPackage for Hardware

It gets a line when the root drops a package addressed to Unknown or Hardware, when the CM fails to close its protocol at shutdown, and when the tests T2 and T7 write to it on purpose. A clean stop adds no line: after a normal headless run the log is empty.

Viewing a file

Open tools/jsonl_viewer.html in a browser and drop output/TestPackage.jsonl on the page; the numeric fields plot.

6. Errors

Errors are not handled yet. This is deliberate for now and replaces the original plan (log, report an error package, keep the root running); a later plan can build on the error-package path that is already there.
  • An error in an actor (in a message or its helper loop) stops that actor. Its Last Ack carries the error to the caller, so an error in the HWM or the CM stops the root, and the root stops the whole tree. Nothing is logged or cleared.
  • The only clean stop is the normal shutdown: Stop on the root's panel, or the Normal Stop of ZM-launcher_test.vi.
  • The root shows every error package addressed to it (destination Root) as JSON in its errors list. Today no actor sends one, so the list stays empty.
  • A failed launch shows in the launcher's error out.
CodeMessageWhenFix
5000<VI>: must be overridden by a child classa bare parent object (ZM-HW-hardware, ZM-CP-communication_protocol) is used where a child was meant, or a child class misses an override. Publishing through a UDP receiver also gives 5000.use the intended child class, or add the missing override

5000 is the only custom code; the catalogue is docs/error-codes.md. The UDP sender clears codes 56 and 66 on purpose, so sending with no listener is silent.

The error run. Run ZM-launcher_test.vi with use_placeholder_hardware = T. The HWM gets the bare ZM-HW-hardware; its first read returns 5000 (source ZM-HW-do.vi: must be overridden by a child class), the HWM stops, and its Last Ack stops the root and the tree. Result: lines_written 0, last_line empty, error_lines 0, ui_errors empty, and error out 1556, because the tree had already stopped when the launcher sent its Normal Stop.

7. Tests

Seven test VIs in ZM-TST-tests.lvlib (folder tests). Each shows a Boolean Pass (the AND of its individual checks, shown beside it) and error out.

T3ZM-TST-hardware.vithe simulated hardware gives varying, in-range test packages; the bare parent returns 5000
T4ZM-TST-protocol.vithe file logger writes each package as one line into the file of its type and appends; the bare protocol returns 5000
T5ZM-TST-udp.viUDP round trip, timeout, silent send with no listener, a multi protocol writing to two file loggers, 5000 from publish on a receiver

T7ZM-TST-routing.vithe root drops packages for Hardware and Unknown with a log line and does not drop Communication

How to run: open a test VI from the tests folder and run it. It needs no running actor tree and returns by itself. It passes when Pass is TRUE and error out shows no error. T5 opens UDP port 61557 itself, so run it while ZM-receiver.vi is stopped.

8. Troubleshooting

The receiver shows nothing.
The tree must be running: start ZM-launcher.vi (the receiver may start before or after it). Keep port at 61557. If its error out shows an error at once, the port is in use, for example by a second ZM-receiver.vi or by T5: stop that and run the receiver again.
The error log already has lines.
T2 writes two marker lines and T7 writes "dropped TestPackage for Hardware" and "... for Unknown" lines on purpose. ZM-launcher_test.vi deletes the log before each run; ZM-launcher.vi does not.
The application stopped by itself.
An error in any actor stops the whole tree (see Errors); it is not logged yet. Run the tests to narrow it down.
Explain Error shows no text for 5000.
The error-code file src/errors/ZM-errors.txt is not installed. Copy it to <LabVIEW 2026>\user.lib\errors\ and restart LabVIEW. Nothing else depends on it.
Many test_* folders under output/.
The tests leave them behind. They are safe to delete.
